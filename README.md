# PocketSmart AI

Budget planning and product recommendations for India. Enter a budget, say what
you need, and get a shopping-ready plan: every rupee assigned, realistic Indian
prices, and direct links to the stores that sell each item.

Three planners:

| Planner | What it does |
| --- | --- |
| **Home interiors** | Splits a budget across lights, ceiling fans, furniture and dining for the rooms you pick. |
| **Party planner** | Costs venue, catering, entertainment, decoration and contingency per guest. |
| **Jewelry** | Reads an outfit photo and suggests pieces that match it, suit the occasion and fit the budget. |

Plans are generated by **Google Gemini** and are always saved to a personal
history. If the AI service is slow, unavailable or misbehaving, a built-in
deterministic engine produces the plan instead, so the app never dead-ends.

---

## Tech stack

- **FastAPI** + **Uvicorn** — web framework and server
- **Jinja2** — server-rendered HTML pages
- **SQLite** (`sqlite3` from the standard library) — users and plan history
- **google-genai** — Gemini access
- **Pydantic** — request validation
- Plain CSS and vanilla JavaScript — no build step, no bundler

## Quick start

```bash
# 1. Create and activate a virtual environment
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux

# 2. Install dependencies
pip install -r requirements.txt

# 3. Configure the environment
copy .env.example .env          # Windows
cp .env.example .env            # macOS / Linux
#    then edit .env and add your Gemini API key

# 4. Run
python main.py
```

Then open <http://127.0.0.1:8000>, create an account, and start planning.

The database (`pocketsmart.db`) and the `static/uploads/` folder are created
automatically on first run.

## Configuration

All settings are read from `.env` (see `config.py`).

> `.env` is **git-ignored** and must never be committed. `cp .env.example .env`
> creates a blank one. The app runs perfectly well with no API key at all - it
> simply stays on the offline engine and shows an "offline mode" banner.

| Variable | Default | Purpose |
| --- | --- | --- |
| `GEMINI_API_KEY` | – | Your Gemini key. `Gemini_Api_Key` and `GOOGLE_API_KEY` are also accepted. |
| `GEMINI_MODEL` | `gemini-3.8-flash` | Model used for planning. |
| `GEMINI_MODEL_FALLBACKS` | `gemini-3.5-flash,gemini-3.7-flash,gemini-flash-latest` | Tried in order if the primary model is retired or unavailable. |
| `FORCE_MOCK_AI` | `false` | Set to `true` to always use the offline engine (for demos and tests). |
| `AI_TIMEOUT_SECONDS` | `30` | Per-attempt time limit. |
| `AI_MAX_ATTEMPTS` | `2` | Attempts before falling back to the offline engine. |
| `SECRET_KEY` | dev placeholder | **Change this in production** – it signs session cookies. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | `720` | Session lifetime. |
| `DATABASE_PATH` | `./pocketsmart.db` | SQLite file location. |
| `HOST` / `PORT` | `127.0.0.1` / `8000` | Dev server bind address. |

## Using the app

1. **Sign up** at `/register`, then log in.
2. Pick a planner from the nav bar (or the dashboard cards).
3. Fill in the short form and press **Generate my plan**.
4. The plan shows a budget summary (budget / allocated / remaining), every item
   with a price and quantity, shopping links per item, and saving tips.
5. Plans are saved automatically — revisit or delete them under **History**.

Every generated plan carries a small engine badge so it is always clear whether
it came from Gemini or from the offline engine.

## JSON API

The same functionality is available over JSON with bearer tokens.

```bash
# 1. Get a token
curl -X POST http://127.0.0.1:8000/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"tester","password":"secret1"}'
# -> {"user": {...}, "access_token": "...", "token_type": "bearer", ...}

# 2. Use it
curl -X POST http://127.0.0.1:8000/api/recommend/home \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{"budget":50000,"lights":5,"ceiling_fans":3,"furniture":4}'
```

| Method | Endpoint | Auth | Purpose |
| --- | --- | --- | --- |
| `GET` | `/api/session` | optional | Who am I? |
| `POST` | `/api/register` | no | Create an account, returns a token |
| `POST` | `/api/login` | no | Returns a bearer token |
| `POST` | `/api/recommend/home` | yes | Interior plan |
| `POST` | `/api/recommend/party` | yes | Party plan |
| `POST` | `/api/recommend/jewelry` | yes | Jewelry plan |
| `GET` | `/api/history` | yes | Saved plans + stats |
| `DELETE` | `/api/history/{id}` | yes | Delete a plan |

Interactive API docs are at <http://127.0.0.1:8000/docs>.

## Project structure

```
config.py               Settings loaded from .env
security.py             PBKDF2 password hashing + signed session tokens
database.py             SQLite schema, users, plans, history, dashboard stats
dependencies.py         Auth dependencies, form parsing, upload validation
main.py                 FastAPI app: pages, form handlers, JSON API, errors
models/schemas.py       Pydantic request/response schemas
services/
  catalog.py            Product/service catalogue and shopping links
  budget.py             INR formatting and budget allocation maths
  gemini_service.py     Gemini client, retries, model fallback, JSON extraction
  local_engine.py       Deterministic offline planner
  recommendation.py     Orchestration: prompts, validation, normalisation
templates/              Jinja2 pages and partials
static/                 CSS, JavaScript, uploaded outfit images
tests/test_app.py       End-to-end test suite
```

### How a plan is produced

1. The form is validated and normalised.
2. `recommendation.py` builds a prompt that includes the relevant part of the
   catalogue so prices stay realistic.
3. `gemini_service.generate()` calls Gemini, enforcing a **wall-clock deadline**
   that the SDK's own timeout does not reliably honour, retrying only genuinely
   transient errors (429/5xx) and falling through to the next model when a model
   name is retired.
4. The reply is parsed leniently (fenced blocks, leading prose, strings
   containing braces) and **normalised**: prices coerced to numbers, line items
   that would exceed the budget trimmed, platform names turned into search
   links.
5. If anything is missing or unusable, the deterministic local engine answers
   instead. Templates never branch on which engine ran.

The blocking Gemini call runs in a worker thread (`run_in_threadpool`), so a
slow AI response can never stall the rest of the server.

## Security

- Passwords are hashed with **PBKDF2-HMAC-SHA256** (260,000 iterations) and a
  per-user random salt — no native crypto dependency.
- Sessions are HMAC-signed, expiring, `HttpOnly`, `SameSite=Lax` cookies.
- Password comparisons and token signatures use `hmac.compare_digest`.
- Every plan query is scoped to the signed-in user, so one account cannot read
  or delete another's plans.
- Uploads are restricted to JPEG/PNG/WebP, capped at 5 MB, and the bytes are
  **magic-number checked** so a renamed script cannot pass as an image. Stored
  filenames are regenerated with a random suffix, never the client's.
- All SQL uses parameterised statements.

**Before deploying:** set a real `SECRET_KEY`, serve over HTTPS and set
`secure=True` on the session cookie in `dependencies.py`.

## Testing

Two suites: a fast API/behaviour one, and a real-browser walkthrough.

### API and behaviour tests

```bash
python tests\test_app.py          # Windows
python tests/test_app.py          # macOS / Linux
```

Runs against a temporary database in mock-AI mode. 59 checks: registration and
login (including duplicates and bad credentials), auth guards on every protected
page, all three planners and their validation errors, upload rejection, history
listing/filtering/deletion, cross-user isolation, and the full JSON API including
token auth and error codes.

### Browser walkthrough (Playwright)

Drives a real Chromium browser through the whole journey - landing, sign-up,
dashboard, all three planners, history, delete, mobile layout, logout - taking a
screenshot at every step into `screenshots/` and asserting on what a person
would actually see. 41 checks.

```bash
# 1. One-time setup (kept in a separate venv so the app deps stay clean)
python -m venv .venv-mcp
.venv-mcp\Scripts\pip install playwright
.venv-mcp\Scripts\python -m playwright install chromium

# 2. Start the app in one terminal
python main.py

# 3. Run the walkthrough in another
set FORCE_MOCK_AI=true
.venv-mcp\Scripts\python tests\browser_walkthrough.py
```

Screenshots land in `screenshots/NN-name.png` and a summary in
`screenshots/walkthrough-report.txt`. Set `BASE_URL` to test a different host.

### Browser MCP server

`tools/browser_mcp.py` exposes the same browser to any MCP client (VS Code,
Cline, Claude Desktop) so the app can be explored interactively rather than by
script. It runs over stdio and is already registered in `.vscode/mcp.json`.

Tools: `browser_navigate`, `browser_click`, `browser_fill`, `browser_select_option`,
`browser_check`, `browser_upload_file`, `browser_submit`, `browser_read_text`,
`browser_count`, `browser_screenshot`, `browser_viewport`,
`browser_console_errors`, `browser_close`.

Environment: `BROWSER_BASE_URL` (default `http://127.0.0.1:8000`),
`BROWSER_HEADLESS` (`0` to watch it work), `BROWSER_TIMEOUT_MS`.

Run it directly with `python tools/browser_mcp.py --help` for usage.

## Limitations

- Prices are **indicative estimates**, not live quotes. Links are search URLs on
  Indian marketplaces, not direct product pages.
- Party catering defaults to a per-guest estimate rather than a real quote.
- The jewelry outfit reading is only as good as the model's analysis; without
  an image it falls back to a neutral blue/casual interpretation.
- The offline engine is a heuristic fallback, not a substitute for the AI plan
  in terms of phrasing and product variety.
- Sessions are cookie-based and stateless; there is no password reset or email
  verification flow.
